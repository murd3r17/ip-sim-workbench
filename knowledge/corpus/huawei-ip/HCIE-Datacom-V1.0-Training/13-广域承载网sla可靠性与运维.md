# 广域承载网SLA、可靠性与运维及Segment Routing概述

## 1. 承载网 SLA 保障新诉求

SLA（Service Level Agreement，服务等级协议）是服务提供商与客户之间定义的正式承诺。在广域网服务领域，SLA 除了包含最基本的连通性需求外，还需要重点关注确定性时延、带宽、可靠性、隔离（安全性）等需求。

通常情况下一条承载路径会承载多种不同类型业务的流量，在相同路径上传输不同业务时，需要根据业务 SLA 的要求提供差分服务。传统的 QoS 通过统计复用的方式，针对业务设置不同的优先级从而保证高优先级业务的流畅体验。但针对隔离、确定性时延需求时，QoS 能力不足。

网络切片能够将承载网络分割成不同服务等级的虚拟网络，针对高质量、高安全需求的业务，提供专用的逻辑通道。

例如：

- 金融企业之间资金结算的业务需要保障高度安全性、时延要足够稳定；
- 企业内部文件传输业务要求高带宽；
- 企业语音业务要求低抖动。

业务常见诉求维度包括：时延、带宽、抖动、丢包率、确定性时延、隔离等。

## 2. 基于切片的承载网：一网多用

IP 网络通过统计复用技术大大提升网络利用率、降低单 bit 传输成本，但同时，统计复用带来网络对不同业务的质量保障等级具有不确定性。按照最高 SLA 要求来准备资源、以满足所有类型的专线及客户是不合适的。综合承载网络需要在多种业务隔离保障与统计复用之间进行平衡，保证各个业务的 SLA 诉求。

利用 FlexE、信道化子接口、QoS 队列等分片资源保留技术，可以将业务划分到各自的业务片中，分片间实现隔离、业务不相互影响，提供不同的 SLA 保障等级。

## 3. QoS 简介

QoS（Quality of Service，服务质量）：针对各种应用的不同需求，为其提供不同的服务质量。通常 QoS 提供以下三种服务模型：

| 服务模型 | 说明 |
| --- | --- |
| Best-Effort Service（尽力而为） | 应用程序可在任何时候发出任意数量的报文；网络尽最大可能发送报文，不承诺时延、可靠性 |
| Integrated Service（综合服务，IntServ） | 应用程序在发送报文前需向网络申请特定服务；网络为应用预留资源，例如 RSVP |
| Differentiated Service（区分服务，DiffServ） | 将网络中的流量分成多个类，为每个类定义相应处理行为，使其拥有不同的优先转发、丢包率、时延等；在 IP 网络中被最广泛应用 |

### 3.1 基于 DiffServ 模型的 QoS 组件

基于 DiffServ 模型的 QoS 有四大组件：流分类和标记（Classification and Marking）、流量监管和整形（Policing and Shaping）、拥塞管理（Congestion management）和拥塞避免（Congestion avoidance）。

- **流分类和标记**：要实现差分服务，需要将数据包分为不同的类别或者设置为不同的优先级。将数据包分为不同的类别称为流分类（不修改原来的数据包）；将数据包设置为不同的优先级称为标记（会修改原来的数据包）。
- **流量限速（流量监管和整形）**：将业务流量限制在特定的速率。当业务流量超过额定速率时，超过的流量将被丢弃或缓存。控制流量接收速率的技术称为流量监管，控制流量发出速率的技术称为流量整形。
- **拥塞管理**：在网络发生拥塞时，将报文放入队列中缓存，并采取某种调度算法安排报文的转发次序。
- **拥塞避免**：监督网络资源的使用情况，当发现拥塞有加剧的趋势时采取主动丢弃报文的策略，从而避免网络过载。

流分类和标记是实现差分服务的前提和基础；流量监管、流量整形、拥塞管理和拥塞避免是从不同方面对网络流量实施控制。

### 3.2 报文转发相关组件说明

- 报文基本转发流程请参考 HCIP-Datacom-Core《认识网络设备》。
- **简单流分类**：只根据 IP 报文的 IP 优先级或 DSCP 值、IPv6 报文的 TC 值、MPLS 报文的 EXP 域值、VLAN 报文的 802.1p 值，对报文进行粗略分类，以识别出具有不同优先级或服务等级特征的流量，实现外部优先级和内部优先级之间的映射。
- **复杂流分类**：采用复杂规则，如由五元组（源地址、源端口号、协议号、目的地址、目的端口号）对报文进行精细分类。
- **PFE（Packet Forwarding Engine，包转发引擎）**：路由器上电启动后运行路由协议学习拓扑、生成路由表；接口板注册成功后，主控板可根据路由表生成转发表项并下发给接口板。执行数据包转发的部件是位于接口板上的 PFE 芯片。
- **TM（Traffic Management，流量管理）**：华为高端路由器接口板上有 TM 芯片及高速缓存。拥塞时数据包以队列形式暂存在缓存里，TM 再按规则调度出队送往交换网；超过缓存容量则按规则丢弃。
- **CAR（Committed Access Rate，承诺接入速率）**：使流量不超过入/出接口允许的带宽，超出限制的数据包会被直接丢弃。目前流量监管使用 CAR，由 PFE 完成：可在上行 PFE 限制不超过入接口带宽，也可在下行 PFE 限制不超过出接口带宽。
- **获取封装信息**：在下行接口板，封装信息需根据转发技术决定，例如 IP 转发获取目的 MAC，MPLS 转发获取标签信息。

### 3.4 流量监管与流量整形

流量监管与流量整形都属于流量限速技术：

- 流量监管：对进入设备的流量监控，限制在允许的流入速率范围；过大则丢弃或重设优先级。
- 流量整形：对输出报文速率控制，使报文以均匀速率发出。

二者都使用令牌桶算法评估流量速率，确定报文是否满足转发条件。

> （原图：流量入 → 流分类和标记 → 流量监管(CAR) → 拥塞管理/避免队列 → 流量整形 → 流量出）

相关调度与拥塞避免概念：

- **WRED（Weighted Random Early Detection）**：对不同优先级数据包或队列设置丢弃策略，在队列拥塞前主动丢弃，实现区分丢弃。
- **FIFO**：不对报文分类；按到达先后进出队列。
- **SP**：严格按队列优先级高低调度；高优先级全部调度完毕后低优先级才有机会。
- **WFQ**：按队列权重分配出口带宽。
- 更多调度算法如 RR、WRR、DRR 等不在此展开。

队列类型说明：

- **PQ 队列**：PQ 之间采用 SP 调度；可对时延敏感业务（如 VoIP）提供绝对优先。缺点是若不限制高优先级带宽，可能造成低优先级饿死。通常只有时延敏感业务入 PQ。
- **WFQ 队列**：按权重调度，对剩余带宽按权重分配。
- **LPQ 队列**：在高速链路（以太网）接口上实现；低速链路（Serial、MP-Group）不支持。LPQ 之间也采用 SP，但拥塞时 PQ 可抢占 WFQ 带宽，而 LPQ 不可抢占 WFQ；PQ 和 WFQ 调度结束后若有剩余带宽再给 LPQ。实际可将 BE 流用 LPQ 调度，负载重时完全限制 BE。
- 8 个端口队列可全部配置为 WFQ / PQ / LPQ，也可组合。

若 CE 或 CE 下游设备不具备流量标记能力，可在广域承载网 PE 入口部署复杂流分类进行流标记入队列，但会相对影响广域承载网转发性能。

### 3.5 广域网 QoS 应用：流调度

广域网转发瓶颈往往在各地区出口广域链路上。例如异地互联采用运营商 MSTP 专线、带宽受限。为防止业务流进入广域链路后在运营商网络被限速丢弃，需要在广域链路出口部署流量整形，保障进入运营商 MSTP 专线的流量不超过限速值。

企业内部业务需合理设计 QoS 策略：核心生产业务或对 QoS 要求高的业务部署 PQ 高优先级调度；对丢包、时延不敏感的业务配置 WFQ，分配基本带宽保障业务不中断即可。

某企业 QoS 设计示例：

| 业务类型 | 重要性 | 优先级 | 调度方式 |
| --- | --- | --- | --- |
| 协议报文 | 高 | CS7/CS6 | PQ |
| 核心业务 | 高 | EF | PQ |
| 视频业务 | 高 | AF4 | PQ |
| 外联业务 | 高 | AF3 | WFQ |
| 办公、测试业务 | 中 | AF2 | WFQ |
| 其他 | 低 | BE | WFQ |

### 3.6 QoS 的不足

QoS 本身不能解决拥塞问题，无法为业务提供隔离和确定性保障：

- QoS 是单跳行为，没有改变网络拓扑架构。
- QoS 不改变业务行为，单条流突发过大时依然可能拥塞。
- QoS 队列少，无法针对特定用户做 SLA 保障，无法提供确定性时延保障。
- QoS 机制是资源管理的经验体系，无法为用户提供独立资源。

逐跳配置、不改变转发路径、无法区分用户、无法提供独立资源。

## 4. HQoS 与信道化子接口

### 4.1 HQoS 为用户提供调度和带宽保障

HQoS（Hierarchical Quality of Service，层次化 QoS）在 QoS 基础上提供对接口资源更细粒度、更多层级化的调度管理，实现对接口资源的精细化分配和管理。每个调度队列可以提供带宽保障，但整个机制仍基于 QoS，也无法满足确定性时延和隔离诉求。

HQoS 层次示例：

1. FQ（Flow Queue，业务队列）
2. SQ（Subscriber Queue，用户队列）
3. GQ（Group Queue，用户组队列）
4. VI（Virtual Interface Queue，虚拟口队列）
5. DQ（Dummy Port Queue，端口队列）

### 4.2 HQoS 各调度器 CIR 不超配

HQoS 增加了 SQ/GQ/VI 等层次化调度器，每个调度器都有 CIR 和 PIR 两个属性，CIR 和 PIR 间采用 SP 调度，优先保障 CIR。HQoS 的带宽保障通过 CIR 严格扣减和 Shaping 实现，所有调度器的 CIR 之和小于端口带宽。

> （原图：多用户 SQ 下挂 CS7/EF/AF/BE 等队列，经 GQ、VI 层次调度）

### 4.3 信道化子接口在 HQoS 上增加管理实体

- **带宽保障**：信道化子接口采用 HQoS 多层次调度实现资源灵活、精细化管理，每个信道化调度树都有独立的缓存资源和带宽资源，可以提供带宽保障。
- **时延保障**：由于信道化子接口间资源严格保障，可以提供一定范围的时延保障。

信道化子接口采用子接口模型，结合 HQoS 机制，独占 HQoS VI/GQ 调度树和带宽，实现严格的调度隔离。

主接口剩余带宽 = 接口带宽 − 所有信道化子接口带宽之和，带宽扣减过程在信道化子接口使能过程自动实现，简化了 HQoS 的应用模型。

信道化子接口提供了管理实体，能够结合控制器实现资源管理，提供端到端资源预留，满足点到多点业务保障诉求。

## 5. FlexE 技术

### 5.1 FlexE 兼容以太网，提供独立资源

FlexE（Flexible Ethernet，灵活以太）是在 MAC 和 PHY 间引入新的技术，是 IP 网络的轻量级增强技术，继承已有的以太标准和 QoS 能力。

- 通过提供隔离的 FlexE 接口链路，可以一张网络实现业务综合承载。
- 通过提供 P2P 的 TDM（Time Division Multiplexing，时分复用）隧道，给每个业务提供独立的资源，满足隔离和确定性时延诉求。

### 5.2 FlexE 基本结构

FlexE 技术通过在 IEEE 802.3 基础上引入 FlexE Shim 层实现了 MAC 与 PHY 层解耦，实现灵活的速率匹配。FlexE 基于 Client/Group 架构，可以支持多个不同 Client 接口速率在 PHY（Group）上映射和传输。

- **Client**：对应于网络的各种用户接口，每个 FlexE 接口可以灵活地从 Group 资源池分配带宽，同时可以进行带宽调整，并通过 64b/66b 编码将数据流传递至 FlexE Shim 层。
- **Group**：本质上就是 IEEE 802.3 标准定义的各种以太网 PHY 层，把 PHY 的带宽池化为 5G、1G（华为设备支持）粒度的资源。
- **Shim**：作为插入传统以太网架构的 MAC 与 PHY 中间的一个额外逻辑层，通过基于 Calendar 的 Slot 分发机制实现 FlexE 技术的核心架构。

## 6. 切片技术比较与实现方式

| 技术 | 特点 |
| --- | --- |
| QoS | 所有流量共享 8 个队列，对资源统一调度，最大化利用统计复用能力；无法区分用户，无法提供独立资源预留 |
| 信道化子接口 | 队列资源隔离，采用多层次调度实现接口资源灵活、精细化管理，提供带宽保障，并且结合控制器提供端到端资源预留 |
| FlexE | 队列和接口资源隔离，各个资源按 TDM 时隙划分，严格隔离，满足资源独享与隔离要求，实现对接口资源灵活、精细化管理 |

### 接口类型说明

| 接口名称 | 应用场景及特性简介 |
| --- | --- |
| FlexE 接口 | 标准以太模式下物理口带宽固定，但通过 FlexE 可将一个或多个物理口使能为灵活以太模式并加入组；组内总带宽可按需灵活分配给组内逻辑口。物理口加入的组称为 FlexE Group，可共享组内物理口带宽的逻辑口称为 FlexE 接口（灵活以太接口/FlexE 业务接口）。通过接口带宽隔离实现业务隔离；相比传统 Trunk，能实现比特级捆绑，解决哈希不均匀；每个 FlexE 接口具备独立 MAC，转发资源隔离，可避免传统逻辑接口头阻塞。可满足移动承载、家庭宽带、专线接入等大端口综合承载，以及 5G 网络分片等需求 |
| VLAN 信道化子接口 | 使能了信道化功能的以太物理端口的子接口。不同类型业务承载在不同信道化子接口上并配置带宽，实现同一物理接口上不同信道化子接口之间带宽严格隔离，解决子接口间业务带宽抢占 |
| 以太网子接口 | 在主接口上配置出来的虚拟接口，具有三层特性，可配置 IP 地址实现 VLAN 间互通。子接口共用主接口物理层参数，又可分别配置各自链路层和网络层参数。禁用/激活子接口不影响主接口；但主接口状态变化会影响子接口，只有主接口连通时子接口才能正常工作 |

### 网络分片与 SliceID 转发示意

- 业务通过不同 VLAN 接入，多个逻辑接口对应网络分片的 VPN 实例 VRF1、VRF2、VRF3……
- Ingress PE 节点为 SliceID 为 2 的网络分片业务流封装 VPN SID 及 SRv6 Policy 隧道信息，同时在 IPv6 Header 与 SRH 扩展头之间插入 Hop-by-Hop SliceID=2 的扩展头。
- 中间各节点逐跳查询 SRH 中的 SRv6 SID 得到物理出接口，再根据 SliceID 查询得到此物理出接口下特定的“资源预留”子接口，Hop-by-Hop SliceID 全程不变。
- Egress PE 节点弹出 Hop-by-Hop 扩展头，根据 VPN SID 转发到对应 VRF 实例的 AC 侧接口。
- 默认分片 SliceID 为 0，不需要插入 IPv6 Hop-by-Hop 扩展头，转发面报文格式与传统 L3VPN over SRv6 Policy 一致。

## 7. 网络可靠性

由于不同广域 VPN 技术的术语不同，本章节将概要性介绍各种保护机制，不展开特定保护技术介绍。

要点：

- MPLS TE 的端到端保护分为热备份（Hot-standby）和普通备份（Ordinary）。热备份是备份路径与主路径同时创建。
- Segment Routing 的局部保护技术较于 FRR 有增强，叫做 TI-LFA（Topology Independent Loop Free Alternate）。
- 快速检测机制：以 BFD 为例，支持快速检测设备间通信故障。
- 传统 LFA 无法形成备份路径的本质在于：分布式网络架构下每台设备独立计算路径，故障瞬间对于最短路径的理解没有共识。

### 7.1 端到端保护的局限

以 Hot-Standby 为例的技术能够保护端到端路径，但不能解决隧道端点 PE 的故障。例如 PE1 和 PE2 建立 TE 隧道且拥有主备路径，若 PE2 发生故障，备份路径无法解决此问题。

> （原图：CE1—PE1—P1/P2/P3/P4—PE2/PE3—CE2，主路径与备份路径示意）

### 7.2 VPN FRR

VPN FRR 利用基于 VPN 的私网路由快速切换技术，通过预先在远端 PE 中设置指向主用 PE 和备用 PE 的主备用转发路径，并结合 PE 故障快速探测，旨在解决 CE 双归 PE 时，PE 节点故障导致的端到端业务收敛时间长的问题。

### 7.3 IP FRR

如果 PE2–CE2 链路故障而 PE2 节点正常，此时 PE1–PE2 的隧道依然可用，因此不需要端到端的隧道切换。PE2 选择 PE3 的路由作为备份下一跳，当 PE2–CE2 链路或 CE2 故障时，快速切换 IP 流量，即 IP FRR。IP FRR 适用于 CE–PE 间的 IP 网络。

### 7.4 小结：网络多级保护

从端到端转发路径看，建议综合采用多级保护：

| 故障位置 | 保护措施 |
| --- | --- |
| CE 接入故障 | 接入侧保护 |
| 隧道中间链路、节点 | 局部/隧道保护 |
| 隧道尾节点 | VPN FRR 等 |
| 远端 CE 故障 | 远端侧保护 |

## 8. 广域网网络管理与运维

在当前各厂家主流广域网解决方案中，推荐采用 SDN 解决方案，由 SDN 控制器集中管理，向转发器下发广域业务。在华为解决方案中，控制器不仅限于“控制”，更融合了“管理”和“分析”。

| 能力 | 说明 | 典型协议/技术 |
| --- | --- | --- |
| 网络分析（管、控、析） | 基于海量网络性能和监控数据，应用 AI 算法获得网络分析结果 | — |
| 网络采集/管理 | 多种协议和通道全面采集网络配置、性能和监控数据；高效配置管理 | NETCONF、Telemetry、SNMP、BGP-LS |
| 网络测量 | 测量网络性能指标（时延、抖动和丢包率等） | TWAMP、iFIT |

> 本图中未呈现隧道技术、流量统计等相关协议。

### 8.1 SNMP

SNMP（Simple Network Management Protocol，简单网络管理协议）是广泛应用于 TCP/IP 网络的网络管理标准协议。SNMP 提供了一种通过运行网络管理软件的中心计算机（NMS）来管理设备的方法。通过“利用网络管理网络”的方式，SNMP 实现了对网络设备的高效和批量管理；同时屏蔽了不同产品之间的差异，实现不同种类和厂商设备的统一管理。

### 8.2 NETCONF

SNMP 并不是面向配置的协议。随着网络规模增大、复杂性增加，SNMP 已不能适应当前复杂网络管理，特别是不能满足配置管理需求。

NETCONF（Network Configuration Protocol，网络配置协议）提供了网管和网络设备之间通信的机制。网络管理员可在网管上增加、修改、删除网络设备配置，获取配置和状态信息。NETCONF 使用 YANG 文件描述设备数据模型；YANG 文件比起 MIB 更具层次化结构。

### 8.3 Telemetry

Telemetry（Network Telemetry，网络遥测技术）主要用于监控网络，包括报文检查和分析、安全入侵和攻击检测、智能收集数据、应用性能管理等。一般配合 NETCONF 使用：分析器分析 Telemetry 收集的数据，与控制器联动，根据分析结果自动修改设备配置等。

Telemetry 优势：

- 基于 YANG 标准模型；
- 采集数据精度高、类型丰富，充分反映网络状况；
- 一次订阅，持续上报；
- 故障定位更快速、精准（亚秒级）。

### 8.4 BGP-LS

BGP-LS（BGP Link State）在 BGP 基础上扩展新的 NLRI。此 NLRI 携带链路、节点和拓扑前缀等信息，又称为链路状态 NLRI。BGP-LS 支持汇总网络层拓扑、带宽、时延等信息，统一上送控制器用于路径计算。

BGP-LS 将网络层各种协议汇总，包括：

- IGP：汇总各 AS 的 IGP 信息；
- TWAMP：测量信息，例如接口时延；
- TE：TE 信息，例如带宽；
- SR：SR 信息，例如 SR 标签。

### 8.5 TWAMP / TWAMP Light

TWAMP Light 是基于标准协议定义的 TWAMP 的轻量级架构。与 TWAMP 标准框架相比，TWAMP Light 简化了建立性能测量会话的控制协议。

- TWAMP 标准版：基于 TCP 协商控制面，测试报文基于 UDP；反射端需要了解 Session 状态，不同厂商可以互通。
- TWAMP Light：无控制面协商过程，测试报文基于 UDP；实现简单、配置简化，反射端无需了解 Session 状态。

**应用场景**：网元设备无需生成和维护统计数据，性能管理系统只需管理网络内性能统计发起节点（TWAMP 客户端）即可获取整网性能统计数据，实现快速、灵活部署 IP 网络性能统计。TWAMP 应用在企业广域网中，可测量任意两个节点间时延、抖动、丢包率，从而为故障排除、流量优化等提供参考依据。

典型流程：

1. 控制器指示网络设备建立性能测量会话（例如 R1 作为 TWAMP Client 主动发起 IP 性能统计）；
2. R1 和 R2 发起 TWAMP 测量会话；
3. R1 将测量结果上报给控制器。

### 8.6 iFIT

iFIT 对端到端业务报文进行测量，从而得到 IP 网络的真实丢包率、时延等性能指标。iFIT 在业务流中插入报文头做染色标记，通过 Telemetry 周期性采集信息，支持端到端时延统计、丢包测量等特性。

补充：

- End.DT4 SID 表示 PE 类型的 Endpoint SID，用于标识网络中的某个 IPv4 VPN 实例。
- 对于 MPLS 报文，iFIT 头插在 MPLS 标签和 MPLS Payload 之间。

**iFIT for SRv6 Policy 场景**：

- iFIT 扩展头封装到 SRH 的 Option TLV 中；
- 支持 SRv6 的节点，能够支持 E2E/逐跳上报 iFIT 统计信息；
- 不支持 SRv6 但支持 IPv6 转发的节点，携带 iFIT 的业务报文可正常转发。

**基于 iFIT 呈现业务路径**：每检测周期，设备上报报文统计计数时，同时上报流表方向、接口、TTL。iMaster NCE-IP 基于各节点上报信息还原该条流的路径信息。不依赖隧道类型（SRv6 / SRv6 Policy / SR-MPLS TE / SR-MPLS BE / MPLS…），也不依赖中间节点是否支持 iFIT。

**基于 iFIT 定位故障点**：结合物理拓扑、质差业务的端节点，基于 iMaster NCE-IP 内置 AI 算法进行路径聚合，寻找到导致业务质差的最小区域，辅助进一步定位定界。

1. 筛选全网质量较差的业务；
2. 智能计算多个业务的公共路径；
3. 选择其中一个业务进行 iFIT 故障检测；
4. 基于逐跳 iFIT 检测定界到故障节点。

### 10.1 产生背景与解决思路

本质上 MPLS 仅是指导数据转发的隧道技术，有完整的隧道创建、隧道管理和维护机制。以上机制都是从网络运营和管理角度驱动的需求，不是由应用驱动网络需求。

传统 IP 数据包转发依赖最短路径到达目的地的 IP 地址。为满足语音、在线游戏、视频会议等业务可靠性要求出现了 FRR；为满足集团客户专线大带宽需求出现了 TE——这些实际都是网络适配业务发展。但业务种类越来越多，不同类型业务对网络要求不尽相同：实时 UC&C（Unified Communications and Collaboration）通常更喜欢低时延、低抖动路径，而大数据应用则更喜欢低丢包率的高带宽通道。若仍按网络适配业务的思路，则不仅无法匹配业务快速发展，还会使网络部署越来越复杂、难以维护。

解决思路是业务驱动网络：由应用（APP）提出需求（时延、带宽、丢包率等），控制器收集网络拓扑、带宽利用率、时延等信息，根据业务需求计算显式路径。

**SR 的解决思路**：

- 简化协议，基于现有协议扩展：扩展后的 IGP/BGP 具有标签分发能力，因此网络中无需 LDP，实现协议简化；设备仅需软件升级，无需硬件更换，保护现网投资。
- 引入源路由机制：通过在头端节点实例化转发策略为标签列表，控制业务流量的转发路径。
- 由业务来定义网络：由应用提出需求，控制器收集信息并按需求计算显式路径。

**SR 解决方案流程**：首先业务提出网络需求（时延、带宽、丢包率等），然后控制器集中计算显式路径，最后下发 SR 路径来承载业务。

### 10.2 SR 概述与优势

SR（Segment Routing，段路由）是基于源路由理念而设计的在网络上转发数据包的一种架构。SR 将网络路径分成一个个段（Segment），并且为这些段和网络中的转发节点分配段标识 ID。通过对段和网络节点进行有序排列（Segment List），就可以得到一条转发路径。

SR 将代表转发路径的段序列编码在数据包头部，随数据包传输。接收端收到数据包后，对段序列进行解析：如果段序列的顶部段标识是本节点，则弹出该标识，然后进行下一步处理；如果不是本节点，则使用 ECMP（Equal Cost Multiple Path，等价负载分担）方式将数据包转发到下一节点。

SR 特点：

- 通过对现有协议（例如 IGP）进行扩展，能使现有网络更好平滑演进；
- 同时支持控制器的集中控制模式和转发器的分布控制模式，提供集中控制与分布控制之间的平衡；
- 采用源路由技术，提供网络和上层应用快速交互的能力。

**SR 的优势**：

| 优势 | 说明 |
| --- | --- |
| 简化 MPLS 网络控制平面 | 使用控制器或 IGP 集中算路和分发标签，不再需要 RSVP-TE、LDP 等隧道协议；可直接应用于 MPLS 架构，转发平面没有变化 |
| 高效 TI-LFA FRR 保护 | 在 SR 基础上结合 RLFA FRR 算法，形成 TI-LFA FRR；支持任意拓扑的节点和链路保护，弥补传统隧道保护不足 |
| 更具网络容量扩展能力 | 传统 MPLS TE 面向连接，需大量 Keepalive；SR 仅在头节点对报文进行标签操作即可控制路径，中间节点不维护路径信息。标签数量≈全网节点数+本地邻接数，与隧道数量和业务规模无关 |
| 更好向 SDN 平滑演进 | 基于源路由，配合集中算路可灵活实现路径控制与调整；同时支持传统网络和 SDN 网络 |

### 10.3 基本概念：Segment 与源路由

**Segment**：节点针对所收到的数据包要执行的指令，该指令包含在数据包头部中。例如：

- 指令1：沿着最短路径到达 R4（支持 ECMP）
- 指令2：沿着 R4 的 GE0/0/2 接口转发数据包
- 指令3：沿着最短路径到达 R8

> 本课程中使用的标签数值仅帮助理解，具体标签分配范围请参考对应产品手册。

**源路由（Source Routing）**：源节点选择一条路径并在报文中压入一个有序的 Segment List，网络中的其他节点按照报文封装的 Segment List 进行转发。

### 10.4 Segment 分类

| Segment 分类 | 说明 |
| --- | --- |
| Prefix Segment（前缀段） | 用于标识网络中的某个目的地址前缀；手工配置；通过 IGP 扩散到其他网元，全局可见、全局有效。Node Segment 是特殊的 Prefix Segment |
| Adjacency Segment（邻接段） | 用于标识网络中的某个邻接；源节点通过协议动态分配；通过 IGP 扩散到其他网元，全局可见、本地有效 |

**Prefix Segment**：

- 用于标识网络中的某个目的地址前缀；通过 IGP 扩散，全局可见、全局有效。
- 通过 Prefix SID（Segment ID）标识。Prefix SID 是发布端通告的 SRGB（Segment Routing Global Block）范围内的偏移值，接收端会根据自己的 SRGB 计算实际标签值用于生成 MPLS 转发表项。
- Node Segment 是特殊的 Prefix Segment，用于标识特定节点。在节点 Loopback 接口下配置 IP 地址作为前缀，这个节点的 Prefix SID 实际就是 Node SID。

**SRGB（Segment Routing Global Block）**：用户指定的为 Segment Routing MPLS 预留的全局标签集合。每台设备通过扩展路由协议通告自己的 SRGB；节点通告前缀 SID 索引（Index）后，各台设备分别根据 SRGB 计算入站及出站 SID。实际部署中建议设备采用统一的 SRGB。

为什么需要 SRGB：SR 要求前缀 SID 全局有效；在 MPLS 中设备的一部分标签空间可能被其他协议（如 LDP）占用，因此需指定明确空间用于 SR 全局标签。

**Adjacency Segment**：用于标识网络中的某个邻接；通过 IGP 扩散，全局可见但仅本地有效。通过 Adjacency SID 标识，为 SRGB 范围之外的本地 SID。

### 10.5 AS 内 Node SID 及 Adjacency SID 的泛洪

SR-MPLS 使用 IGP 协议进行拓扑信息、前缀信息、SRGB 和标签信息的通告。IGP 为完成上述功能，对协议报文的 TLV 进行了扩展。

#### OSPF for SR-MPLS

| 名称 | 作用 | 携带位置 |
| --- | --- | --- |
| SR-Algorithm TLV | 对外通告自己使用的算法 | Type 10 Opaque LSA |
| SID/Label Range TLV | 通告 SR-MPLS 的 SID 或 MPLS Label 范围 | Type 10 Opaque LSA |
| SRMS Preference TLV | 通告网元作为 SR Mapping Server 的优先级 | Type 10 Opaque LSA |
| SID/Label Sub-TLV | 通告 SR-MPLS 的 SID 或 MPLS Label | OSPFv2 Extended Prefix Opaque LSA 中的相关 TLV |
| Prefix SID Sub-TLV | 通告 SR-MPLS 的 Prefix SID | OSPFv2 Extended Prefix Opaque LSA / Extended Prefix Range TLV |
| Adj-SID Sub-TLV | 在 P2P 网络中通告 Adjacency SID | OSPFv2 Extended Link Opaque LSA 中的 Extended Link TLV |
| LAN Adj-SID Sub-TLV | 在 LAN 网络中通告 Adjacency SID | OSPFv2 Extended Link Opaque LSA 中的 Extended Link TLV |

#### IS-IS for SR-MPLS

| 名称 | 作用 | 携带位置（示例） |
| --- | --- | --- |
| Prefix-SID Sub-TLV | 通告 Prefix SID | TLV-135 / 235 / 236 / 237 等 |
| Adj-SID Sub-TLV | P2P 网络通告 Adjacency SID | TLV-22 / 23 / 141 / 222 / 223 等 |
| LAN-Adj-SID Sub-TLV | LAN 网络通告 Adjacency SID | 同上 |
| SID/Label Binding TLV | 通告 SID 或 MPLS Label；通告前缀到 SID 的映射 | IS-IS LSP |
| SR-Capabilities Sub-TLV | 对外通告 SR-MPLS 能力 | IS-IS Router Capability TLV-242 |
| SR Local Block Sub-TLV | 通告网元为本地 SID 预留的标签范围 | IS-IS Router Capability TLV-242 |

### 10.6 SR Policy 基本概念

RFC 8402 中定义 SR Policy 是一段有序的段列表（an ordered list of segments）。更完整地说，SR Policy 最终呈现为一段有序的段列表，还包含计算、生成和维护这个段列表及引入流量等 SR 技术的一种框架。SR Policy 是当前最主流的实现 SR 的方式。

段列表由一系列优化目标和限制（例如时延、亲和性和 SRLG 等）综合计算得到；计算可由本地或者控制器完成，然后应用到网络中。

SR Policy 可以由 CLI、NETCONF、PCEP、BGP SR Policy 等多种方式生成，包含 Segment List，完整地指导流量引入和转发。

### 10.7 SR-MPLS 与 SRv6

| 对比项 | SR-MPLS | SRv6 |
| --- | --- | --- |
| 数据转发平面 | 基于 MPLS | 基于 IPv6 |
| SID | 使用 MPLS 标签值作为 SID | 使用 IPv6 地址作为 SID |
| 段序列编码 | 编码为标签栈；要处理的段位于栈顶；处理完成后相关标签弹出 | 使用 IPv6 扩展头 SRH（Segment Routing Header）承载 |

### 10.8 标签栈、粘连标签与粘连节点

- **标签栈**：标签的排序集合，用于标识一条完整的 LSP。栈中每一个邻接标签标识一条具体邻接，整个标签栈标识整条转发路径 LSP 的所有邻接。转发过程中通过栈顶邻接标签查找对应邻接并弹出后转发；所有邻接标签弹出后到达隧道目的地。
- **粘连标签与粘连节点**：当标签栈深度超过转发器所支持的深度时，控制器需为转发器分配多个标签栈，在合适节点下发标签栈的同时分配一种特殊标签，将这些标签栈关联起来实现逐段转发。这种特殊标签称为粘连标签，该节点称为粘连节点；控制器为粘连节点分配粘连标签，并将其压在标签栈底。

### 10.9 SID 的使用与转发场景

通过按序组合前缀（节点）SID 和邻接 SID，可以构建出网络内的任何路径。在路径中的每一跳，使用栈顶段信息区分下一跳；段信息按顺序堆叠在数据头顶部。

- 当栈顶段信息包含另一个节点的标识时，接收节点使用 ECMP 将数据包转发到下一跳；
- 当栈顶段信息是本节点的标识时，接收节点弹出顶部段并执行下一个段所需的任务。

实际应用中 Prefix Segment、Adjacency Segment 可以单独使用，也可以结合使用。

**场景1：基于 Prefix Segment 的转发路径**

1. 通过 IGP 扩散之后，整个 IGP 域的所有设备学习到 R2 的 Prefix SID；
2. 以 R1 为例，它通过 SPF 算法计算出一条到达 R2 的最短路径。

基于 Prefix Segment 的转发路径并不是一条固定路径。

**场景2：基于 Adjacency Segment 的转发路径**

通过 Adjacency Segment 的 Segment List，可以严格指定任意路径，可更好配合流量工程。

**场景3：基于 Adjacency Segment + Node Segment 的转发路径**

将二者结合：通过 Adjacency Segment 可强制整条路径包含某一个邻接；对于 Node Segment，节点可使用 SPF 计算最短路径，也可以负载分担。这种方式的路径并不是严格固定，称作松散路径（Loose Explicit）。

### 10.10 SR-MPLS BE

使用 SID 来指导设备基于最短路径进行数据转发，这种工作机制称为 SR-MPLS BE（Best Effort）。例如使用 R6 的 Node SID 可以指导数据沿着去往 R6 的最短路径转发，该最短路径基于路由协议计算得出，并且支持等价路径。
